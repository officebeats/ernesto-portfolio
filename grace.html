Case Study

Grace
a multi-agent AI system for patient access.

One steering agent routes each patient request to a specialized agent with a defined contract — book, verify, cancel, change, answer — on Google Cloud and Vertex AI.

A case study by Ernesto Rodriguez — AI Product Lead at Ascension Health, November 2024 to April 2026.

I designed and led Grace as Ascension's AI Product Lead. Following my tenure, the system scaled to live volume across Ascension's contact center — press coverage of that live operation appears below.

Overview

Scale turns small failure rates
into real harm.

Grace was designed at Ascension Health — 95 hospitals and $25.3B in revenue in fiscal 2025 — where patient scheduling and support calls arrive at high volume, every day.

Callers range from simple requests (confirm, cancel, reschedule) to complex ones (new primary care appointments). At that scale, a small failure rate is a large number of patients. That is why the design put control and review ahead of automation rate.

The Challenge

Patients waited.
Staff repeated the same work.

Scheduling and support demand exceeded what human teams could absorb cleanly. Simple calls crowded out complex ones, and inconsistent handling hurt the patient experience.

This was never a "replace the call center" problem. It is a routing and trust problem: which requests can an agent close safely, and which must reach a person fast — with a clear record of what happened either way?

The system

One steering agent.
Many atomic agents.

The steering agent decides

A steering agent reads each incoming request and routes it to the right handler — a specialized agent, or a human. It decides who should handle a request before anyone answers it.

Atomic agents act

Each atomic agent does exactly one job: book, verify, cancel, change, or answer. One job per agent keeps every agent narrow, testable, and replaceable.

Contracts, not prompts

Agents connect under A2A agent cards and contracts: each agent states what it accepts, what it returns, and what it must not do. Behavior is written down, reviewable, and testable before it reaches a patient.

Built on GCP and Vertex AI

The system runs on Google Cloud and Vertex AI, on top of a unified patient record harmonized across the health system's many EHRs.

Architecture

Control first.
Automation second.

Narrow agents fail in narrow ways

A booking agent cannot drift into giving medical advice. A single general agent is simpler to build and harder to govern — and in healthcare, governable wins.

Behavior is reviewable before patients see it

Contracts make each agent's behavior something a team can read, test, and approve in advance — not something discovered in production.

Every interaction leaves a trace

Routing keeps a full record: which agent acted, under which contract, with what result. Failures get reviewed agent by agent instead of guessed at.

Humans stay in the loop by design

The human path is part of the design, not a fallback after failure. Requests the system should not close alone go to people — fast, and with context.

Quality & Safety

Every answer had to
earn its way out.

Voice of the customer

Voice-of-customer reviews ran on a set cadence and fed design changes — the loop that kept prioritization grounded in patient feedback and quality improving throughout my tenure.

A "do not answer" path

Low-confidence or out-of-scope cases route to humans instead of guessing. An agent system needs a "do not answer" path as much as it needs good answers.

Traceability

Each interaction can be reviewed after the fact, agent by agent — which agent acted, under which contract, with what result.

My Evaluation Approach

Confidence gates and
a human-review path.

The same evaluation pattern runs through my work: score agent output, then gate on confidence — below the bar, the case goes to a human instead of shipping a weak answer. Grace's design routes low-confidence cases to people; my CleanQuest work applies the same pattern at project scale.

0.6 confidence gate

In CleanQuest, cloud grades count as verified only at confidence ≥ 0.6. Below that, cases are marked NOT SCORED and routed to human review rather than forced to a number.

Judge setup is part of the product

Two hosts running the same model scored a standardized demo pair differently — Baseten 98/100, Fireworks 96/100. Identical model, different host, different score: judge configuration is part of the product surface, and I test it like product code.

Design Decisions

Decisions
that held up.

Routing before generation. Decide who should handle a request before anyone answers it.

Contracts over prompts. Behavior written down, reviewable, and testable per agent.

A human path by design — not as a fallback after failure. These three choices are why the system scaled to live volume after my tenure without a redesign.
